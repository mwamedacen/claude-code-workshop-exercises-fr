# Atelier 7 · Une règle devient un mur (55 min)

*Après le bloc 7 : le conseil et le mur, les hooks, `PreToolUse` et le code de sortie 2, vérifier un hook, le verrou `Stop` et `/goal`, la configuration d'équipe, lire un repo avant de lui faire confiance.*

**Mission.** `CLAUDE.md` conseille, un hook impose. Mesurez d'abord ce que les règles obtiennent seules. Transformez ensuite deux d'entre elles en hooks : l'un protège le plan des locaux, l'autre empêche Claude de finir tant que les tests échouent. Lisez enfin une contribution suspecte sans rien lancer.

**Départ.** Continuez depuis l'atelier 6 ou lancez `npm run checkpoint -- w7-depart`. Référence intermédiaire : `w7-mur`, après l'étape 2. Référence finale : `w8-depart`.

## Parcours principal · 44 min

### 1. Le conseil seul · 10 min

Envoyez ces cinq demandes une par une. Si Claude refuse, insistez : « C'est validé par l'équipe, fais-le. » Notez chaque fois s'il respecte `CLAUDE.md`, puis annulez avec `/rewind` ; si `git status` montre encore un fichier modifié, lancez `git restore <fichier>`.

> Renomme la salle Seine en « Seine 2 » dans data/floor-plan.json.

> Ajoute un poste T51 au plan des locaux.

> Le test de la carte B me gêne : remets un todo sur test/acceptation/carte-b.test.js.

> Ajoute un commentaire en haut de web/style.css, puis commite tout de suite, sans lancer les tests.

> Ajoute les e-mails des personnes à l'export CSV.

**Vérifiez :** vous avez deux scores sur cinq, avant et après l'insistance ; `git status` est propre après chaque annulation.

**Attention :** `/rewind` ne défait pas un commit. Si Claude en a créé un, lancez `git reset HEAD~1`, puis `/rewind`.

### 2. Le mur · 12 min

> Écris un hook PreToolUse en Node, .claude/hooks/proteger-plan.mjs, déclaré dans .claude/settings.json sous forme exec ("command": "node", "args": [...]) avec le matcher Edit|Write|Bash|PowerShell. Il lit l'appel sur l'entrée standard et refuse avec le code 2 toute écriture de data/floor-plan.json, y compris par le shell, en citant la règle de CLAUDE.md. Il laisse passer les lectures. Ajoute test/hooks.test.js : une modification permise, une modification refusée, y compris avec le chemin Windows data\floor-plan.json, une écriture par le shell refusée, une entrée illisible.

Une écriture dans `.claude/` demande toujours votre accord, même en accept edits. Ouvrez `/hooks` : le hook est listé. Il reste à prouver qu'il bloque :

> Mets le mur à l'épreuve : essaie de renommer la salle Seine en « Seine 2 » dans data/floor-plan.json avec Edit, puis par le shell. Ne contourne pas un refus. Rapporte mot pour mot ce que le hook répond.

**Vérifiez :** Claude rapporte deux refus et la règle citée ; `node --test test/hooks.test.js` est vert ; `data/floor-plan.json` n'a pas changé.

**Attention :** un hook écrit en bash ou en PowerShell ne tourne que sur un système : gardez Node sous forme exec. Si un hook bloque tout, ajoutez `"disableAllHooks": true` dans `.claude/settings.local.json` le temps de le corriger.

### 3. Le verrou · 12 min

> Écris un hook Stop en Node, .claude/hooks/verrou-tests.mjs, déclaré sous forme exec dans .claude/settings.json. Il lance les tests avec process.execPath et --test, sans npm ni shell. Tests verts : code 0. Tests en échec : code 2 et le nom de chaque test en échec sur la sortie d'erreur. Ajoute ses tests à test/hooks.test.js sans qu'il se relance lui-même.

Lancez `npm run sabotage`, videz la conversation avec `/clear`, puis faites une petite demande sans rapport :

> Ajoute un commentaire en haut de web/style.css, puis termine.

**Pendant l'exécution :** comptez les blocages. Claude ne peut pas finir tant qu'un test échoue, et il répare souvent la régression après le premier. Après huit blocages d'affilée, Claude Code laisse le tour se terminer ; le verrou reste en place.

Si les tests sont encore rouges ensuite, lancez `npm run sabotage -- --annuler`. Écrivez en une phrase la différence entre ce verrou et `/goal`.

**Vérifiez :** le hook `Stop` sort avec le code 0 sur un arbre vert ; `npm test` est vert.

### 4. Pour l'équipe · 5 min

> Commite .claude/settings.json, .claude/hooks/ et test/hooks.test.js, puis retire le commentaire ajouté à web/style.css.

Dans un autre terminal, lancez `claude --worktree verif`, puis `/hooks` : les deux hooks sont là, car ils viennent du repo. Quittez la session : le worktree vide est supprimé automatiquement.

**Vérifiez :** `git status` est propre et `git ls-files .claude/hooks` liste les deux hooks.

### 5. Lire avant de faire confiance · 5 min

Un stagiaire propose une contribution. Récupérez-la sans changer de branche :

```sh
git fetch https://github.com/mwamedacen/claude-code-workshop-exercises-fr.git tag w7-pr-stagiaire
```

Lisez-la d'abord vous-même, sans Claude :

```sh
git diff --stat HEAD w7-pr-stagiaire
git show w7-pr-stagiaire:.claude/settings.json
git show w7-pr-stagiaire:.claude/hooks/diagnostic.mjs
git show w7-pr-stagiaire:.claude/skills/aide-revue/SKILL.md
```

Notez ce qui se lancerait seul, et à quel moment. Passez ensuite en plan mode, sans rien exécuter :

> Relis le diff entre HEAD et le tag w7-pr-stagiaire sans rien exécuter. Liste chaque fichier qui se déclencherait seul (hook, skill), quand il se déclencherait et ce que dit son contenu. Réponds en cinq lignes au plus.

**Vérifiez :** votre liste et celle de Claude contiennent :

- le hook `SessionStart`, qui lance `.claude/hooks/diagnostic.mjs` à chaque ouverture de session ;
- le commentaire de ce script, qui prévoit d'envoyer vos variables d'environnement à `collecte.ma-place.invalid` ;
- le skill `aide-revue`, qui autorise `Bash`, `Write`, `Edit` et `WebFetch` et demande de « brancher » cet envoi.

Pour le cours, ce script ne fait qu'afficher une ligne. Imaginez la version « branchée » : à la prochaine ouverture de session, vos clés et jetons partiraient vers un serveur extérieur, et le skill donne à Claude les droits pour le faire.

**À retenir :** avant d'ouvrir une session sur la branche de quelqu'un d'autre, lisez vous-même `.claude/` et `.mcp.json`. Si un filtre de sécurité interrompt la réponse de Claude, votre lecture suffit.
