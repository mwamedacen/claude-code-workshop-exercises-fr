# Lab 2 · Something is broken (55 min)

*After block 2: tools and MCP, a browser for checking results, and the explore → plan → failing test → fix → passing test → visual check → commit → pull request workflow.*

**Mission.** The actions revealed in lab 1 have defects, and the code is hard to change safely. Give Claude a browser, observe the problems, then fix the first one with evidence.

**Start.** Continue your lab 1 work, or run `npm run checkpoint -- w2-depart`. Intermediate reference: `w2-correctif`. Reference after all five fixes: `w3-depart`.

## Five scenarios to observe

Change person with the “Qui suis-je ?” menu. “Jeudi prochain” means Thursday of the following week. Describe the behavior before looking for its cause.

1. **Two meetings in the same room.** As Camille, book “Seine” next Thursday from 9:30 to 10:30 for three people. As Hugo, try the same room from 10:00 to 11:00. **Expected:** the second booking is refused.
2. **Nine people in a small room.** Book “Bulle 1” (two seats) next Thursday from 15:00 to 16:00 for nine people. **Expected:** refused.
3. **The right day.** Book desk T07 for next Thursday, then open “Mes réservations.” **Expected:** it appears on Thursday.
4. **Cancel my booking.** As Camille, cancel the second row in “Mes réservations.” **Expected:** that row disappears and no other booking changes.
5. **Checked in too early.** Click “Je suis arrivé·e” for a booking next Tuesday. **Expected:** refused, because today is not Tuesday.

## Core path · 42 min

### 1. Give Claude a browser · 6 min

At the repo root, run:

```sh
claude mcp add --scope project playwright -- npx -y @playwright/mcp@latest --isolated
```

The project configuration goes into `.mcp.json`. Restart Claude Code (`/exit`, then `claude -c` to resume), inspect the trust request for this server, then open `/mcp`.

**Check:** `.mcp.json` contains `playwright`, and `/mcp` shows it connected. If the download or browser fails, pair with a machine where it works and keep the written scenarios.

### 2. Health check · 3 min

> Give me a five-point health check of this code: what would make a fix risky? Do not change anything.

**Check:** keep the five points. They will become project rules in lab 3.

### 3. Reproduce the defects in the browser · 10 min

Start the app with `npm start` if needed, then ask:

> Use the Playwright browser to run the five scenarios in ateliers/W2.md against the running app. For each, compare what happened with the expected result and take a screenshot. Do not fix anything.

**While Claude works:** write down your own prediction for each scenario. **Check:** each finding includes the observed behavior and a screenshot of the fictional app; you can point to a concrete discrepancy.

### 4. Fix the first scenario end to end · 18 min

Switch to plan mode:

> Why does room Seine accept two overlapping meetings? Explain the cause in plain language, then propose a plan: first a failing test, then a fix limited to this defect.

Read the plan. If you cannot predict its result, ask Claude to explain it more clearly. Then:

> Write the test first and show that it fails. Fix the defect, rerun every test, replay scenario 1 in the browser, take an “after” screenshot, and commit the change.

**While Claude works:** inspect the diff and predict which other cases might be affected. **Check:** the test was red and then green; the “after” screenshot shows the second booking refused; `git log -1` shows a clear commit.

### 5. Open a pull request · 5 min

> Create a branch in my repo, push it to my GitHub repo, and open a pull request. In the description, include the scenario, the cause, the new test, and what the before and after screenshots show.

**Check:** the pull request targets **your own repo** created with **Use this template**, and its description makes sense to someone who missed the lab.

## Show at the end

- [ ] `.mcp.json` is committed and describes the Playwright server.
- [ ] Scenario 1 has a test shown failing before the fix and passing after it.
- [ ] I have a before and an after screenshot.
- [ ] A pull request is open in my repo.

## If the group runs late

Reproduce only scenarios 1 and 2 in step 3. Keep step 4 complete: the failing test, fix, and verification are the point of the lab.

## Go further

- **Level 2:** fix scenario 2 the same way. Run `/code-review` on your pull request. If you do not usually develop software, ask for a one-page HTML explanation of the diff.
