# Atelier 2 · Ça ne marche pas (55 min)

*Après le bloc 2 : les outils et MCP, le navigateur pour vérifier un résultat, et la séquence explorer → planifier → test rouge → correction → test vert → vérification visuelle → commit → pull request.*

**Mission.** Les actions révélées à l'atelier 1 ont des défauts et le code est difficile à modifier sans risque. Donnez un navigateur à Claude, observez les problèmes, puis corrigez le premier avec des preuves.

**Départ.** Continuez votre travail de l'atelier 1 ou lancez `npm run checkpoint -- w2-depart`. Référence intermédiaire : `w2-correctif`. Référence après les cinq corrections : `w3-depart`.

## Cinq scénarios à observer

Changez de personne avec le menu « Qui suis-je ? ». « Jeudi prochain » désigne le jeudi de la semaine suivante. Décrivez ce qui se passe avant d'en chercher la cause.

1. **Deux réunions dans la même salle.** En tant que Camille, réservez « Seine » jeudi prochain de 9 h 30 à 10 h 30 pour trois personnes. En tant que Hugo, essayez la même salle de 10 h à 11 h. **Attendu :** la seconde réservation est refusée.
2. **Neuf personnes dans une petite salle.** Réservez « Bulle 1 » (deux places) jeudi prochain de 15 h à 16 h pour neuf personnes. **Attendu :** refus.
3. **Le bon jour.** Réservez le poste T07 jeudi prochain, puis ouvrez « Mes réservations ». **Attendu :** la réservation figure le jeudi.
4. **Annuler ma réservation.** En tant que Camille, annulez la deuxième ligne de « Mes réservations ». **Attendu :** cette ligne disparaît et aucune autre réservation ne change.
5. **Arrivée trop tôt.** Cliquez sur « Je suis arrivé·e » pour une réservation de mardi prochain. **Attendu :** refus, car nous ne sommes pas mardi.

## Parcours principal · 42 min

### 1. Donner un navigateur à Claude · 6 min

À la racine du repo, lancez :

```sh
claude mcp add --scope project playwright -- npx -y @playwright/mcp@latest --isolated
```

La configuration du projet va dans `.mcp.json`. Redémarrez Claude Code (`/exit`, puis `claude -c` pour reprendre), examinez la demande de confiance pour ce serveur, puis ouvrez `/mcp`.

**Vérifiez :** `.mcp.json` contient `playwright` et `/mcp` le montre connecté. Si le téléchargement ou le navigateur échoue, travaillez à deux sur une machine où il fonctionne et conservez les scénarios écrits.

### 2. Bilan de santé · 3 min

> Donne-moi un bilan de santé de ce code en cinq points : qu'est-ce qui rendrait une correction risquée ? Ne change rien.

**Vérifiez :** gardez ces cinq points. Ils deviendront des règles du projet à l'atelier 3.

### 3. Reproduire les défauts dans le navigateur · 10 min

Démarrez l'application avec `npm start` si nécessaire, puis demandez :

> Utilise le navigateur Playwright pour exécuter les cinq scénarios de ateliers/W2.md dans l'application ouverte. Pour chacun, compare le comportement observé au résultat attendu et prends une capture d'écran. Ne corrige rien.

**Pendant l'exécution :** notez votre propre prédiction pour chaque scénario. **Vérifiez :** chaque constat contient le comportement observé et une capture de l'application fictive ; vous pouvez montrer un écart concret.

### 4. Corriger le premier scénario de bout en bout · 18 min

Passez en plan mode :

> Pourquoi la salle Seine accepte-t-elle deux réunions qui se chevauchent ? Explique la cause simplement, puis propose un plan : d'abord un test qui échoue, ensuite une correction limitée à ce défaut.

Lisez le plan. Si vous ne pouvez pas prédire le résultat, demandez à Claude de le clarifier. Puis :

> Écris d'abord le test et montre qu'il échoue. Corrige le défaut, relance tous les tests, rejoue le scénario 1 dans le navigateur, prends une capture « après » et crée un commit.

**Pendant l'exécution :** examinez le diff et prédisez les autres cas qui pourraient changer. **Vérifiez :** le test était rouge puis vert ; la capture « après » montre le refus de la seconde réservation ; `git log -1` affiche un commit clair.

### 5. Ouvrir une pull request · 5 min

> Crée une branche dans mon repo, pousse-la vers mon repo GitHub et ouvre une pull request. Dans la description, indique le scénario, la cause, le nouveau test et ce que montrent les captures avant et après.

**Vérifiez :** la pull request vise **votre propre repo** créé avec **Use this template** et sa description est compréhensible par une personne absente de l'atelier.

## À montrer à la fin

- [ ] `.mcp.json` est commité et décrit le serveur Playwright.
- [ ] Un test du scénario 1 a échoué avant la correction et réussi après.
- [ ] J'ai une capture avant et une capture après.
- [ ] Une pull request est ouverte dans mon repo.

## Si le groupe prend du retard

Ne reproduisez que les scénarios 1 et 2 à l'étape 3. Gardez toute l'étape 4 : le test rouge, la correction et la vérification sont essentiels.

## Pour aller plus loin

- **Niveau 2 :** corrigez le scénario 2 de la même manière. Lancez `/code-review` sur votre pull request. Si vous ne développez pas habituellement, demandez une explication du diff dans une page HTML.
- **Niveau 3 :** corrigez les scénarios 3 à 5. Rejouez un cas avec Claude in Chrome si votre accès le permet. Essayez le plugin officiel `mcp-server-dev` pour un petit serveur répondant à « Quelles salles sont libres ? ».
- **Encore du temps :** choisissez une carte de `BACKLOG.md` et écrivez une vérification qui échoue avant la correction.
